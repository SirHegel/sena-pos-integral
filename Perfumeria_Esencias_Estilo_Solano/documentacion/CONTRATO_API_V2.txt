Versión de contrato: PS-API-V2-r3.
Contrato de implementación PS — API /api/v2, aislada backend 8095/frontend 8094/MySQL 33193.
Solicitudes y respuestas de datos usan snake_case. JSON numbers de cantidades/importes se envían preferentemente como strings decimales; servidor BigDecimal. Listados devuelven array; GET detalle devuelve objeto; POST alta devuelve {id:UUID}; POST acción devuelve detalle o {id}. Errores {codigo,mensaje}, HTTP400/401/403/404/409.
Autenticación: GET /auth/sesion → {autenticado:boolean,csrf:string,actor?:{usuario_id,nombre,perfil}}. POST /auth/login {nombre_acceso,clave} devuelve misma forma; POST /auth/logout. Cookie sesión y header X-CSRF-Token en escrituras, mismo origen. Roles ADMINISTRADOR/VENDEDORA. No empresa/tenant en esta adaptación de un local.
GET /inicio → resumen stock,alertas,cartera,ventas día; GET /usuarios. POST /usuarios {nombre_visible,nombre_acceso,clave,perfil}. Admin.
GET/POST /clientes {nombre,contacto_cobranza?}. GET/POST /proveedores {nombre,contacto?}. GET/POST /fragancias {codigo_interno,nombre_comercial}. Vendedora puede alta cliente; otros admin.
GET /articulos → [articulo_id,codigo,nombre,unidad_base,clase,funcion_material,minimo_base,saldo_base,costo_promedio_cop,alerta]. POST /articulos {codigo,nombre,unidad_base:ML|UNIDAD|G,clase:LIQUIDO|ENVASE|ACCESORIO|PERFUME_SELLADO|PERFUME_ABIERTO|MUESTRA,funcion_material:ESENCIA|ALCOHOL|FIJADOR|FEROMONAS|FRASCO|VALVULA|TAPA|ETIQUETA|ATOMIZADOR|PERFUME|OTRO,contenido_nominal_ml?,minimo_base}. PUT /articulos/{id}/minimo {minimo_base}. GET /movimientos?articulo_id=.
GET /formulas → array con componentes. POST /formulas {fragancia_id,variante:NORMAL|EXTRA_FIJADOR|EXTRA_FEROMONAS,volumen_preparado_ml,componentes:[{articulo_id,cantidad_ml_por_preparacion}]}. Suma exacta volumen. Crea versión aprobada por administrador en la configuración de fórmulas.
GET /ofertas → array {oferta_id,codigo_venta,nombre_venta,modalidad,volumen_ml,precio_cop,especificacion_id,formula_id,componentes:[{articulo_id,cantidad_base}],disponible_unidades}. POST /ofertas {codigo_venta,nombre_venta,modalidad:TERMINADO|PREPARACION|RECARGA|DECANT|ADICIONAL,fragancia_id?,volumen_ml?,formula_id?,precio_cop?,componentes:[{articulo_id,cantidad_base}]}. Precio null permite configurar, pero no emitir venta hasta fijarlo. PUT /ofertas/{id}/precio {importe_unitario_cop}; nueva vigencia. PUT /ofertas/{id}/suministro {formula_id?,componentes:[...]} crea nueva versión, no modifica usada. PREPARACION exige frasco de capacidad correspondiente, válvula, tapa y etiqueta. RECARGA usa fórmula y etiqueta opcional. DECANT exige un perfume abierto por su volumen exacto, un atomizador de capacidad correspondiente y una etiqueta. Las funciones de materiales se validan con metadatos tipados; no se infieren del nombre del artículo. No se añaden líquidos fuera de la fórmula en preparación o recarga.
GET /recepciones. POST /recepciones {proveedor_id,documento_proveedor,clave_operacion,lineas:[{articulo_id,cantidad,unidad_codigo:ML|L|UNIDAD|G,costo_total_cop}]}. Stock y costo promedio ponderado se actualizan atómicamente. /recepciones/{id} detalle.
POST /aperturas {articulo_sellado_id,articulo_abierto_id,unidades,volumen_util_ml,motivo,clave_operacion}. Admin. Consume sellado UNIDAD y genera ML en abierto, sin superar contenido_nominal_ml*unidades. Costo transferido, no compra ficticia.
GET /ventas; GET /ventas/{id} → venta+lineas+cobros+total_cop+cobrado_cop+saldo_cop+descuento_cop+estado_pago. POST /ventas {cliente_id?,lineas:[{especificacion_id,unidades}]} crea BORRADOR con precio actual. POST /ventas/{id}/descuento {importe_cop,motivo} admin. POST /ventas/{id}/emitir {clave_operacion,credito:boolean,fecha_vencimiento?,condicion_pactada?,cobro?:{turno_id,medio,importe_cop,referencia_externa?,confirmado:true}}. Contado (credito:false) exige cobro anidado por total exacto y ejecuta cobro+entrega+consumo en una sola transacción. Fiado (credito:true) exige cliente, vencimiento y autorización Admin; no admite cobro anidado, y consume al entregar. Los abonos posteriores no vuelven a descontar inventario. estado_pago derivado SIN_PAGO/PARCIAL/PAGADA.
POST /ventas/{id}/cobros {turno_id,medio:EFECTIVO|NEQUI|DAVIPLATA|TARJETA,importe_cop,referencia_externa?,confirmado:true,clave_operacion}. No sobrepago. Electrónico requiere referencia y confirmación humana, no API bancaria. GET /cartera → ventas crédito con saldo/vencimiento/cliente. GET /ventas/{id}/comprobante → mismo detalle con naturaleza recibo académico, no DIAN.
GET /turnos, GET /turnos/{id} → turno+cobros/egresos+esperado_efectivo_cop+totales_por_medio. POST /turnos {caja_id?,fondo_cop} abre propia (si no caja_id usa caja única configurada). POST /turnos/{id}/cerrar {conciliaciones:[{medio,importe_verificado_cop,soporte_privado_ref?}],observacion}. Las4conciliaciones requeridas. Mantiene diferencias con signo; no inventa cierre sin diferencia.
GET /incidencias. POST /incidencias {tipo:MERMA|MUESTRA|REPOSICION|DEVOLUCION,venta_id?,linea_no?,motivo,clave_operacion,lineas:[{articulo_id,cantidad_base,direccion:SALIDA|ENTRADA,costo_unitario_base_cop?}],turno_id?,devolucion_cop?}. Admin. MERMA física adicional sólo se descuenta si cantidad real sale de stock; reclasificar mezcla ya consumida usa sin lineas/sin nuevo stock. Entrada utilizable de devolución requiere líneas explícitas; no retorno automático.
GET /gastos. POST /gastos {fecha,concepto,importe_cop,documento_ref,turno_id?,medio:EFECTIVO|NEQUI|DAVIPLATA|TARJETA,clave_operacion}. Admin. Afecta caja si turno+efectivo. No crea doble egreso.
GET /reportes?tipo=ventas|medios|rotacion|costos|vendedoras|gastos|devoluciones&desde=YYYY-MM-DD&hasta=YYYY-MM-DD → {filas:[...],desde,hasta,tipo}. Admin; Vendedora reportes propios de ventas. Cantidades heterogéneas no se suman. Costos se reconocen a promedio ponderado al entregar; resultado mostrado margen_bruto_cop, no nómina/ganancia neta. GET /exportacion.xlsx?mes=YYYY-MM → archivo XLSX de cinco hojas Ventas/Cobros/Gastos/Cartera/Devoluciones para contador. No CSV disfrazado.
GET /configuracion → unidades, medios,cajas. No seeds de datos privados del negocio. Fixtures DEMO sólo mediante script de prueba aislado, nunca datos reales precargados.

Cierre del contrato r3: MERMA/MUESTRA rechazan ENTRADA; factura del mismo proveedor no se repite con otra clave. Reembolso efectivo exige DEVOLUCION ligada a venta emitida/linea y turno abierto, nunca supera cobrado menos devuelto y crea un solo movimiento SALIDA con incidencia_id. No altera el recibo original ni genera retorno físico implícito. Retorno físico exige cantidad utilizable explícita y conserva costo del suministro; no puede superar lo suministrado menos retornos previos. Reportes conservan importe/margen bruto original y agregan devoluciones acumuladas, ingreso y costo ajustados y margen bruto ajustado; no representan beneficio neto. Devoluciones del XLSX se filtran por fecha del reembolso, incluso de ventas anteriores. Cartera representa saldo vigente al generar (naturaleza_corte/consultada_en_utc), no cierre histórico del mes. Timestamp HTTP UTC explícito terminado en Z.
GET/POST /conteos son Admin: {observacion?,renglones:[{articulo_id,cantidad_medida,unidad_medicion,observacion?}]}; conserva medición y saldo esperado del instante sin ajustar stock. Cantidades UNIDAD deben ser enteras. Artículo con movimientos sin valoración mantiene costo_promedio_cop:null y valoracion_pendiente:true para Admin y bloquea salida/apertura; no se sustituye por cero.
Huella idempotente usa serialización binaria tipada con longitudes/mapas ordenados; incluye operación para recepción/apertura e identidad de venta para cobros. Contraseñas no se recortan y admiten como máximo72bytesUTF8 (mínimo10 caracteres para altas).
